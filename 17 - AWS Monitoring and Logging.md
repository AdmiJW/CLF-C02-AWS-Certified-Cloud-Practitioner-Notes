# 1 - Introduction to AWS Monitoring and Logging Services

## **1.1 Overview of AWS Monitoring and Logging Services**

AWS provides services to **monitor resource performance, track account activities, troubleshoot applications, and maintain operational visibility**.

The four services covered in this section are:

| AWS Service              | Primary Purpose                    | Key Use Case                                           |
| ------------------------ | ---------------------------------- | ------------------------------------------------------ |
| **Amazon CloudWatch**    | Monitoring and performance metrics | Monitor AWS resource health and performance            |
| **AWS CloudTrail**       | API activity tracking and auditing | Identify who performed actions in an AWS account       |
| **AWS X-Ray**            | Application tracing                | Trace and troubleshoot application requests            |
| **AWS Health Dashboard** | AWS service health information     | View AWS service issues and events affecting resources |

**Amazon CloudWatch** and **AWS CloudTrail** are particularly important for the **CLF-C02 exam**.

## **1.2 Amazon CloudWatch vs AWS CloudTrail**

### **Amazon CloudWatch - Monitoring**

**Amazon CloudWatch** is a monitoring service that provides visibility into the **performance and operational health of AWS resources**.
- Collects **metrics** from AWS services and resources.
- Provides **dashboards** to visualize resource performance and health.
- Helps monitor the operational status of AWS infrastructure.

**Example scenario:**

A company wants to monitor the performance and health of its Amazon EC2 instances.

**Use Amazon CloudWatch** to collect metrics and visualize resource performance.

### **AWS CloudTrail - Auditing**

**AWS CloudTrail** records **AWS API activity** performed within an AWS account.
- Tracks actions performed by users and other identities.
- Records activities such as:
    - Creating an **Amazon EC2 instance**.
    - Deleting an **EC2 instance**.
    - Modifying an **Amazon EBS volume**.
- Helps identify **who performed an action** within an AWS account.
- Supports **security auditing, governance, and accountability**.

**Example scenario:**

An EC2 instance was deleted, and an administrator needs to determine which user performed the action.

**Use AWS CloudTrail** to investigate the recorded API activity.

### **Key Differences**

|Feature|Amazon CloudWatch|AWS CloudTrail|
|---|---|---|
|**Primary purpose**|Monitoring|Auditing|
|**Focus**|Resource performance and health|AWS API activity|
|**Information collected**|Metrics and operational data|API activity records|
|**Key question**|How are my resources performing?|Who performed an action?|
|**Typical use case**|Monitor EC2 performance|Identify who deleted an EC2 instance|

**Key distinction:**

- **CloudWatch** - What is happening with resource performance and health?
- **CloudTrail** - Who performed an action in the AWS account?

## **1.3 Exam Focus**

- **Monitor AWS resource performance and health - Amazon CloudWatch**
- **Collect and visualize resource metrics - Amazon CloudWatch**
- **Create monitoring dashboards - Amazon CloudWatch**
- **Record AWS API activity - AWS CloudTrail**
- **Identify who created, modified, or deleted an AWS resource - AWS CloudTrail**
- **Security auditing and account activity tracking - AWS CloudTrail**
- **Trace application requests - AWS X-Ray**
- **View AWS service health issues - AWS Health Dashboard**

**Most important exam distinction: CloudWatch = Monitoring; CloudTrail = Auditing.**

# 2 - Amazon CloudWatch

## **2.1 Amazon CloudWatch Overview**

**Amazon CloudWatch** is an AWS **monitoring and observability service** that collects and tracks **metrics, logs, and events** from AWS resources and applications.

It provides centralized visibility into the **performance, health, and operational status** of applications and infrastructure.

### **Key Features**

- **Metrics** - Collect and monitor performance measurements from AWS resources.
- **Logs** - Collect and analyze logs generated by AWS services and applications.
- **Alarms** - Trigger notifications or automated actions when defined thresholds are breached.
- **Dashboards** - Visualize monitoring data in a centralized dashboard.
- **Historical Data** - Analyze performance trends over time.
- **Integration** - Monitor AWS resources, on-premises environments, and third-party applications.

CloudWatch provides **near-real-time monitoring** and historical performance data.

### **Example CloudWatch Metrics**

| AWS Resource    | Example Metric                                 |
| --------------- | ---------------------------------------------- |
| **Amazon EC2**  | CPU utilization                                |
| **Amazon EBS**  | Disk IOPS (Input/Output Operations Per Second) |
| **Amazon S3**   | Number of requests                             |
| **Application** | Custom business metrics, such as sales amounts |

### **How Amazon CloudWatch Works**

1. AWS resources, applications, or on-premises servers send **metrics and logs** to CloudWatch.
2. CloudWatch collects and stores this monitoring data.
3. **CloudWatch Dashboards** visualize resource performance and operational health.
4. **CloudWatch Alarms** evaluate metrics against configured thresholds.
5. When an alarm is triggered, CloudWatch can initiate actions such as:
    - Sending notifications.
    - Invoking **AWS Lambda** functions.
    - Adjusting **Amazon EC2 Auto Scaling** capacity.
    - Stopping, terminating, or rebooting EC2 instances.

**Example scenario:**

An application experiences high CPU utilization on its EC2 instances.

CloudWatch can monitor CPU utilization and trigger an alarm when it exceeds a predefined threshold. This alarm can initiate an **Auto Scaling** action to adjust capacity.

## **2.2 Amazon CloudWatch Metrics**

**CloudWatch Metrics** are numerical measurements of **system or application performance at a specific point in time**.
- Metrics represent performance parameters, such as CPU utilization or disk IOPS.
- Each metric contains a value associated with a timestamp.
- Metric values change over time and form **time-series data**.
- Historical metric data can be analyzed to identify performance trends.
- Metrics can be used to create **CloudWatch Alarms**.

### **Basic Monitoring vs Detailed Monitoring**

CloudWatch supports two monitoring levels for Amazon EC2:

|Feature|Basic Monitoring|Detailed Monitoring|
|---|---|---|
|**Collection interval**|Every 5 minutes|Every 1 minute|
|**Cost**|Free|Additional charges|
|**Monitoring frequency**|Lower|Higher|
|**Use case**|Standard resource monitoring|Faster detection of performance changes|

**Key distinction:**

- **Basic Monitoring** - Metrics collected every **5 minutes**, at no additional charge.
- **Detailed Monitoring** - Metrics collected every **1 minute**, with additional charges.

Detailed Monitoring provides more frequent performance measurements.

### **CloudWatch Custom Metrics**

**Custom Metrics** allow users to publish their own application-specific or business-specific measurements to CloudWatch.
- Not limited to predefined metrics provided by AWS services.
- Can monitor application or business performance.
- Can be displayed on dashboards and used to create alarms.

**Example scenario:**

An e-commerce application wants to track the value of every sale.

The application can publish each sales amount as a **CloudWatch Custom Metric** to analyze sales performance over time.

**Exam clue: Monitor application-specific business data - CloudWatch Custom Metrics.**

## **2.3 Amazon CloudWatch Alarms**

**CloudWatch Alarms** monitor metrics and trigger actions when predefined conditions or **thresholds** are met.

For example, an alarm can be configured to detect when EC2 CPU utilization exceeds a specified percentage.

### **CloudWatch Alarm States**

CloudWatch Alarms have **three possible states**:

| State                         | Meaning                                                           |
| ----------------------------- | ----------------------------------------------------------------- |
| **OK**                        | The monitored metric is within the configured threshold.          |
| **ALARM**                     | The metric has breached the configured threshold.                 |
| **INSUFFICIENT****_****DATA** | Not enough metric data is available to determine the alarm state. |

**INSUFFICIENT****_****DATA** can occur when an alarm is newly created and CloudWatch has not yet received enough monitoring data.

### **CloudWatch Alarm Actions**

When an alarm changes state, it can trigger automated actions.

| Alarm Action                | Purpose                                            |
| --------------------------- | -------------------------------------------------- |
| **Notifications**           | Send alerts, including SMS notifications           |
| **AWS Lambda**              | Invoke a function to perform automated actions     |
| **Amazon EC2 Auto Scaling** | Adjust the number of EC2 instances based on demand |
| **EC2 Actions**             | Stop, terminate, or reboot an EC2 instance         |

### **Example Scenario**

An application running on EC2 experiences increasing traffic.
1. CloudWatch monitors **CPU utilization**.
2. A CloudWatch Alarm detects that CPU utilization exceeds the configured threshold.
3. The alarm triggers an **Auto Scaling** action.
4. The Auto Scaling group adjusts EC2 capacity to handle the increased load.

CloudWatch Alarms can also be based on **log-derived metrics**, such as the number of error messages detected within a specified period.

**Exam clue: Automatically respond when a monitoring threshold is breached - CloudWatch Alarms.**

## **2.4 Amazon CloudWatch Logs**

**Amazon CloudWatch Logs** provides centralized collection, storage, and analysis of logs generated by AWS services and applications.

### **Log Sources**

CloudWatch Logs can collect logs from:
- **Amazon EC2** instances.
- **Amazon ECS** containers.
- **AWS Elastic Beanstalk** applications.
- **AWS CloudTrail**.
- **Amazon Route 53** DNS services.
- **On-premises servers**.

Centralized logging allows administrators to investigate errors and monitor application behavior from a single service.

### **Collecting Logs from EC2**

**EC2 instance operating system and application logs are not automatically collected by CloudWatch.**

To collect these logs:
1. Install the **Amazon CloudWatch Agent** on the EC2 instance.
2. Configure the agent to collect and send the required logs.
3. Attach an appropriate **IAM role** granting the instance permission to send logs to CloudWatch.

The CloudWatch Agent can also collect logs from **on-premises servers**.

**Exam clue: Collect EC2 application or operating system logs - CloudWatch Agent.**

### **CloudWatch Logs Retention**

By default, **CloudWatch Logs are retained indefinitely** unless a retention policy is configured.

Retention can be customized to control storage duration and cost.

Examples include:
- 1 day
- 7 days
- 30 days
- Indefinite retention

**Key concept:** Longer log retention can increase storage costs.

### **CloudWatch Logs Storage Classes**

CloudWatch Logs provides different storage classes depending on log access requirements.

| Storage Class         | Purpose                                                  | Cost Consideration       |
| --------------------- | -------------------------------------------------------- | ------------------------ |
| **Standard**          | Default log storage for regular monitoring and analysis  | Standard storage pricing |
| **Infrequent Access** | Cost-effective storage for logs accessed less frequently | Lower storage cost       |

**Exam clue: Store logs that are accessed infrequently at a lower storage cost - CloudWatch Logs Infrequent Access.**

### **CloudWatch Logs Insights**

**CloudWatch Logs Insights** allows users to **search, query, filter, and analyze log data** using a specialized query language.

Common use cases include:
- Searching for error messages.
- Filtering logs by keywords.
- Investigating application failures.
- Analyzing log patterns.

**Example scenario:**

An application generates thousands of log entries, and an administrator needs to identify entries containing error messages.

**Use CloudWatch Logs Insights** to query and filter the relevant log data.

## **2.5 Exam Focus**

- **Monitor AWS resource and application performance - Amazon CloudWatch**
- **Track CPU utilization, disk IOPS, and other performance measurements - CloudWatch Metrics**
- **Visualize monitoring data - CloudWatch Dashboards**
- **Basic Monitoring - 5-minute metrics, free**
- **Detailed Monitoring - 1-minute metrics, additional cost**
- **Track application-specific business data - CloudWatch Custom Metrics**
- **Trigger actions when thresholds are breached - CloudWatch Alarms**
- **Three alarm states - OK, ALARM, INSUFFICIENT****_****DATA**
- **Automatically adjust EC2 capacity based on monitoring thresholds - CloudWatch Alarms with EC2 Auto Scaling**
- **Centralized collection and storage of application logs - CloudWatch Logs**
- **Collect EC2 operating system and application logs - CloudWatch Agent with appropriate IAM permissions**
- **Default CloudWatch Logs retention - Indefinite**
- **Lower-cost storage for infrequently accessed logs - CloudWatch Logs Infrequent Access**
- **Search and analyze logs using queries - CloudWatch Logs Insights**

**Key exam distinction:**

- **CloudWatch Metrics** - Measure performance.
- **CloudWatch Alarms** - Detect threshold breaches and trigger actions.
- **CloudWatch Logs** - Collect and store log data.
- **CloudWatch Logs Insights** - Query and analyze collected logs.

# 3 - \[Exercise] Create a CloudWatch Alarm for EC2

## **3.1 CloudWatch Alarm with Amazon SNS**

**Amazon CloudWatch Alarms** can monitor EC2 performance metrics and automatically send notifications when predefined thresholds are breached.

In this exercise, a CloudWatch Alarm monitors **EC2 CPU utilization** and sends an **email notification** through **Amazon Simple Notification Service (Amazon SNS)** when CPU utilization exceeds **50%**.

### **AWS Services Involved**

| Service               | Purpose                                                 |
| --------------------- | ------------------------------------------------------- |
| **Amazon EC2**        | Provides the instance being monitored                   |
| **Amazon CloudWatch** | Monitors CPU utilization and evaluates alarm conditions |
| **Amazon SNS**        | Sends email notifications when the alarm is triggered   |

### **Amazon SNS - Notification Service**

**Amazon Simple Notification Service (Amazon SNS)** is a managed messaging service used to send notifications to subscribers.

Key concepts:
- **SNS Topic** - A communication channel used to distribute notifications.
- **SNS Subscription** - Defines the destination that receives messages from a topic.
- **Email Protocol** - Allows notifications to be delivered to an email address.
- **Subscription Confirmation** - Email subscribers must confirm their subscription before receiving notifications.

**Key distinction:**
- **CloudWatch** - Detects when a metric breaches a threshold.
- **Amazon SNS** - Delivers the notification to subscribers.

## **3.2 CloudWatch Alarm Configuration**

A CloudWatch Alarm is configured to monitor the **CPUUtilization** metric of a specific EC2 instance.

|Configuration|Example Value|
|---|---|
|**Resource**|Amazon EC2 instance|
|**Metric**|CPUUtilization|
|**Statistic**|Average|
|**Threshold**|Greater than 50%|
|**Alarm condition**|Average CPU utilization exceeds 50%|
|**Alarm action**|Publish notification to an SNS topic|
|**Notification destination**|Subscribed email address|

### **Alarm Workflow**

1. Create an **SNS topic** and subscribe an email address.
2. Confirm the email subscription.
3. Configure a **CloudWatch Alarm** for the EC2 CPUUtilization metric.
4. Set the threshold to **greater than 50%**.
5. Associate the alarm with the SNS topic.
6. When the threshold is breached, CloudWatch enters the **ALARM** state and sends a notification through SNS.

### **Alarm State Changes**

| State                 | Meaning                                                   |
| --------------------- | --------------------------------------------------------- |
| **INSUFFICIENT_DATA** | Not enough metric data is available to evaluate the alarm |
| **OK**                | CPU utilization is within the configured threshold        |
| **ALARM**             | CPU utilization breaches the configured threshold         |

A newly created alarm may initially display **INSUFFICIENT****_****DATA** until sufficient metric data becomes available.

## **3.3 Testing the CloudWatch Alarm**

To test the alarm, CPU load is artificially increased on the EC2 instance using the **stress** utility.
- The stress utility generates high CPU utilization.
- CloudWatch collects the CPU utilization metric.
- With **EC2 Basic Monitoring**, metrics are collected at **5-minute intervals**.
- Once sufficient data indicates that CPU utilization exceeds **50%**, the alarm enters the **ALARM** state.
- CloudWatch publishes a notification to the configured **SNS topic**.
- SNS delivers an email to the confirmed subscriber.

**Example result:**

An EC2 instance reaches approximately **100% CPU utilization**, causing the CloudWatch Alarm to trigger and an email notification to be delivered.

**Important:** Alarm evaluation depends on the configured monitoring period and available metric data, so notifications are not necessarily immediate.

## **3.4 Exam Focus**

- **Monitor EC2 CPU utilization - Amazon CloudWatch**
- **Detect CPU utilization above a defined threshold - CloudWatch Alarm**
- **Send email notifications when an alarm triggers - Amazon SNS**
- **Communication channel for notifications - SNS Topic**
- **Receive SNS email notifications - Confirmed SNS Subscription**
- **Basic EC2 Monitoring - 5-minute metric intervals**
- **Insufficient metric data - INSUFFICIENT****_****DATA**
- **Metric threshold breached - ALARM**
- **Metric within the configured threshold - OK**

**Key exam distinction:**

- **Amazon CloudWatch** - Monitors metrics and detects threshold breaches.
- **Amazon SNS** - Delivers notifications when alarms are triggered.

**Exam scenario:** A company wants to receive an email whenever an EC2 instance exceeds a specified CPU utilization threshold.

**Correct solution - Amazon CloudWatch Alarm integrated with Amazon SNS.**

# 4 - Amazon CloudTrail \[Important]

## **4.1 AWS CloudTrail Overview**

**AWS CloudTrail** is an AWS service that records **API activity and user actions** performed within an AWS account.

It helps answer three important questions:
- **Who** performed an action?
- **What** action was performed?
- **When** was the action performed?

CloudTrail provides visibility into AWS account activities and is primarily used for **security auditing, governance, and compliance**.

### **Key Features**

- Records **AWS API calls** made within an AWS account.
- Tracks activities performed by **IAM users, IAM roles, and AWS services**.
- Captures information about the action, resource, identity, and timestamp.
- Helps investigate **suspicious or unauthorized activities**.
- Provides an **Event History** of recent account activities.
- Integrates with **Amazon S3** and **Amazon CloudWatch Logs** for storing and analyzing events.

**AWS CloudTrail Event History is enabled by default** in AWS accounts across all AWS Regions.

## **4.2 AWS CloudTrail Events**

A **CloudTrail Event** is a record of an activity or API call performed within an AWS account.

### **Activities Captured by CloudTrail**

CloudTrail records API activity initiated through different AWS access methods:

| Access Method              | Example                                           |
| -------------------------- | ------------------------------------------------- |
| **AWS Management Console** | User terminates an EC2 instance                   |
| **AWS CLI**                | User executes a command to modify an AWS resource |
| **AWS SDK**                | Application invokes an AWS API                    |
| **Direct AWS API Calls**   | API request sent directly to an AWS service       |

Activities can be performed by:
- **IAM Users** - Individual users accessing AWS resources.
- **IAM Roles** - Assumed identities performing AWS actions.
- **AWS Services** - Services making API calls to other AWS services.

### **Information Recorded in CloudTrail Events**

A CloudTrail event can contain the following information:

| Event Information        | Description                                           |
| ------------------------ | ----------------------------------------------------- |
| **User Identity**        | IAM user or role associated with the action           |
| **Event Name**           | API operation performed, such as `TerminateInstances` |
| **Event Time**           | When the action occurred                              |
| **AWS Service**          | Service involved in the API call                      |
| **AWS Region**           | Region where the event occurred                       |
| **Source IP Address**    | IP address from which the request originated          |
| **Resource Information** | AWS resource affected by the action                   |
| **Account ID**           | AWS account associated with the event                 |

### **Example Scenario**

An EC2 instance was unexpectedly terminated, and an administrator needs to determine who performed the action.

**AWS CloudTrail** can provide information such as:
- The IAM identity responsible for terminating the instance.
- The time the termination occurred.
- The AWS Region and EC2 instance involved.
- The source IP address associated with the API request.

**Exam clue: Identify who deleted, modified, or created an AWS resource - AWS CloudTrail.**

## **4.3 AWS CloudTrail Event History and Log Storage**

CloudTrail provides different ways to access and analyze recorded AWS API activities.

### **CloudTrail Event History**

**CloudTrail Event History** allows users to view recent AWS account activities directly from the AWS Management Console.
- Available by default.
- Provides access to the **last 90 days of management events**.
- Allows administrators to investigate recent API activity.
- Does not require creating a trail to view recent management events.

### **CloudTrail Integration with Other AWS Services**

CloudTrail events can also be delivered to other AWS services for storage and analysis.

| AWS Service                      | Purpose                                               |
| -------------------------------- | ----------------------------------------------------- |
| **AWS CloudTrail Event History** | View recent account activity for the last 90 days     |
| **Amazon S3**                    | Store CloudTrail logs for longer-term retention       |
| **Amazon CloudWatch Logs**       | Analyze and monitor CloudTrail log events             |
| **Amazon Athena**                | Query and analyze CloudTrail logs stored in Amazon S3 |

### **Long-Term Log Storage**

To retain CloudTrail events beyond the default Event History window, a **CloudTrail Trail** can be configured to deliver log files to an **Amazon S3 bucket**.
- **Amazon S3** provides storage for historical CloudTrail logs.
- **Amazon Athena** can query CloudTrail logs stored in S3.
- **Amazon CloudWatch Logs** can be used for log monitoring and analysis.

**Key distinction:**

- **Recent API activity (last 90 days) - CloudTrail Event History**
- **Long-term API activity retention - CloudTrail logs stored in Amazon S3**
- **Query historical CloudTrail logs in S3 - Amazon Athena**

## **4.4 Amazon CloudWatch vs AWS CloudTrail**

Both services provide visibility into AWS environments, but they serve different purposes.

| Feature               | Amazon CloudWatch                                  | AWS CloudTrail                            |
| --------------------- | -------------------------------------------------- | ----------------------------------------- |
| **Primary purpose**   | Monitoring and observability                       | API activity tracking and auditing        |
| **Focus**             | Resource performance and operational health        | Actions performed within AWS accounts     |
| **Data collected**    | Metrics, logs, and events                          | AWS API activity records                  |
| **Common use case**   | Monitor EC2 CPU utilization                        | Identify who terminated an EC2 instance   |
| **Security use case** | Monitor operational conditions and generate alarms | Investigate suspicious account activities |
| **Key question**      | How are my resources performing?                   | Who did what, and when?                   |

### **Example Exam Scenarios**

**Scenario 1:** A company wants to monitor CPU utilization for its EC2 instances.

**Correct service - Amazon CloudWatch**

**Scenario 2:** A security administrator wants to determine which IAM user deleted an S3 bucket.

**Correct service - AWS CloudTrail**

**Scenario 3:** An organization needs to retain AWS API activity logs for long-term auditing.

**Correct solution - AWS CloudTrail with Amazon S3**

**Scenario 4:** An administrator wants to query historical CloudTrail logs stored in an S3 bucket.

**Correct service - Amazon Athena**

## **4.5 Exam Focus**

- **Track AWS API activity - AWS CloudTrail**
- **Identify who performed an AWS action and when - AWS CloudTrail**
- **Security auditing and investigation of suspicious activities - AWS CloudTrail**
- **Record API activity from AWS Console, CLI, and SDK - AWS CloudTrail**

# 5 - Amazon X-Ray

## **5.1 AWS X-Ray Overview**

**AWS X-Ray** is an AWS service used for **distributed tracing, application debugging, and performance analysis**, particularly in **microservices architectures**.

It helps developers understand how requests travel through different application services and identify performance issues or failures.

### **Key Features**

- **Distributed Tracing** - Tracks user requests across multiple application services.
- **Troubleshooting** - Identifies which service caused an application failure.
- **Performance Analysis** - Detects slow responses and performance bottlenecks.
- **Service Visualization** - Provides visual representations of interactions between application components.
- **Request Analysis** - Helps understand the complete path of a request through an application.

### **AWS X-Ray in Microservices Architecture**

A **microservices architecture** divides an application into smaller, independent services that communicate with each other.

For example, an e-commerce application may contain:
- **Frontend Service** - Handles user interactions.
- **Backend Service** - Processes application requests.
- **Order Service** - Manages customer orders.
- **Payment Service** - Processes payments.
- **Database Service** - Stores application data.

When a user places an order, the request may pass through several services.

If the order fails, **AWS X-Ray** helps identify which service caused the failure by tracing the request across the application.

**Exam clue: Troubleshoot failures across interconnected microservices - AWS X-Ray.**

## **5.2 How AWS X-Ray Works**

AWS X-Ray collects **trace data** about requests processed by an application.

### **Request Tracing Process**

1. An application receives a user request.
2. The application uses the **AWS X-Ray SDK** to collect tracing information.
3. Trace data is sent through the **X-Ray daemon** to the X-Ray service.
4. AWS X-Ray provides visualizations of the interactions between application components.
5. Developers analyze the traces to identify errors, latency, and performance bottlenecks.

### **Information Provided by AWS X-Ray**

| Information                 | Purpose                                                   |
| --------------------------- | --------------------------------------------------------- |
| **Request Path**            | Shows how a request travels between services              |
| **Response Time**           | Measures how long each service takes to process a request |
| **Errors**                  | Helps identify which service failed                       |
| **Service Dependencies**    | Shows how application components communicate              |
| **Performance Bottlenecks** | Identifies services causing delays                        |

### **Common Use Cases**

**AWS X-Ray** is useful for:
- **Debugging slow responses** - Identify services causing high latency.
- **Troubleshooting errors** - Determine which service is responsible for application failures.
- **Tracing requests** - Understand the complete journey of a user request.
- **Performance Optimization** - Identify bottlenecks affecting application performance.
- **Service-Level Monitoring** - Analyze whether services meet expected response times.

### **Example Scenario**

An e-commerce application uses multiple microservices to process customer orders.

Customers report that orders are taking too long to complete.

Using **AWS X-Ray**, developers can trace requests through the frontend, backend, payment, and database services to identify which component is causing the delay.

**Correct service - AWS X-Ray**

## **5.3 AWS X-Ray vs Amazon CloudWatch vs AWS CloudTrail**

| AWS Service           | Primary Purpose                                | Exam Clue                                  |
| --------------------- | ---------------------------------------------- | ------------------------------------------ |
| **AWS X-Ray**         | Distributed tracing and application debugging  | Identify slow or failing microservices     |
| **Amazon CloudWatch** | Resource monitoring, metrics, logs, and alarms | Monitor CPU utilization or resource health |
| **AWS CloudTrail**    | API activity tracking and auditing             | Identify who performed an AWS action       |

**Key distinctions:**

- **AWS X-Ray** - Which application service is causing a failure or delay?
- **Amazon CloudWatch** - How are AWS resources performing?
- **AWS CloudTrail** - Who performed an action in the AWS account?

## **5.4 Exam Focus**

- **Distributed tracing across microservices - AWS X-Ray**
- **Troubleshoot application failures - AWS X-Ray**
- **Identify slow application responses and performance bottlenecks - AWS X-Ray**
- **Trace the path of a user request across multiple services - AWS X-Ray**
- **Visualize service interactions and dependencies - AWS X-Ray**
- **Monitor resource performance and metrics - Amazon CloudWatch**
- **Audit AWS API activity - AWS CloudTrail**

**Most important exam distinction:**

- **AWS X-Ray - Application request tracing and debugging.**
- **Amazon CloudWatch - Resource performance monitoring.**
- **AWS CloudTrail - AWS API activity auditing.**

# 6 - AWS Health Dashboard

## **6.1 AWS Health Dashboard Overview**

**AWS Health Dashboard** provides information about **AWS service availability, operational issues, and outages** across AWS Regions.

It helps customers identify whether an application problem is caused by an **AWS service disruption** rather than an issue with their own infrastructure or application.

### **Key Features**

- **Service Health Monitoring** - Displays operational issues affecting AWS services.
- **Regional Outage Information** - Identifies service disruptions in specific AWS Regions.
- **Service Health History** - Provides information about past AWS service disruptions.
- **Personalized Health Information** - Identifies AWS issues that may affect resources in your account.
- **Notifications** - Alerts customers about relevant AWS service issues.
- **Remediation Recommendations** - Provides guidance to help customers respond to disruptions.

**Example scenario:**

An application cannot access Amazon S3, even though its configuration appears correct.

The administrator can check **AWS Health Dashboard** to determine whether Amazon S3 is experiencing an AWS-side service disruption.

## **6.2 AWS Service Health vs Account Health**

AWS Health Dashboard provides two important types of health information.

### **AWS Service Health**

**Service Health** provides information about the operational status of AWS services across different AWS Regions.
- Displays **current AWS service disruptions**.
- Identifies which AWS services and Regions are affected.
- Provides **historical service health information**.
- Shows information relevant to AWS customers generally.

**Example:**

Amazon API Gateway experiences a service disruption in the **US East (Ohio)** Region.

AWS Service Health provides information about the disruption, allowing customers to determine whether their applications might be affected.

### **AWS Account Health**

**Account Health** provides personalized information about AWS service events that may directly affect resources in a specific AWS account.
- Identifies service disruptions relevant to **your AWS resources**.
- Provides notifications about potentially affected services.
- Offers recommendations for handling or mitigating disruptions.
- Helps determine whether an AWS service event directly impacts your environment.

**Example:**

An AWS service experiences an outage, but your AWS account does not use that service.

The disruption may appear in general **AWS Service Health**, but it may not directly affect your account.

### **Key Differences**

| Feature                 | AWS Service Health                                     | AWS Account Health                                 |
| ----------------------- | ------------------------------------------------------ | -------------------------------------------------- |
| **Scope**               | General AWS service availability                       | Personalized account impact                        |
| **Information**         | Service outages and regional disruptions               | Issues affecting your AWS resources                |
| **Audience**            | AWS customers generally                                | Individual AWS account                             |
| **Primary use case**    | Check whether an AWS service is experiencing an outage | Determine whether an outage affects your resources |
| **Additional guidance** | General service status information                     | Notifications and remediation recommendations      |

**Key distinction:**

- **AWS Service Health** - Is an AWS service experiencing an outage?
- **AWS Account Health** - Is an AWS service issue affecting my AWS account?

## **6.3 AWS Health Dashboard vs Other Monitoring Services**

| AWS Service              | Primary Purpose                                      | Exam Clue                                              |
| ------------------------ | ---------------------------------------------------- | ------------------------------------------------------ |
| **AWS Health Dashboard** | Monitor AWS service health and outages               | Check whether AWS is experiencing a service disruption |
